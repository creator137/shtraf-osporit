# Стадия 2: распознавание документа и ручная корректировка

## Цель стадии

Добавить обработку загруженного постановления: распознать текст документа,
сохранить результат, извлечь базовые поля и дать оператору проверить и
исправить данные в админке.

Стадия 2 не включает юридический анализ, оценку шансов, генерацию жалобы и
интеграции с государственными системами. Здесь мы готовим качественную карточку
постановления как основу для следующих стадий.

## Обязательный функционал

### Backend

- Модель для хранения результата распознавания документа.
- Модель или поля для карточки постановления.
- Сохранение raw OCR text.
- Сохранение извлечённых структурированных полей.
- Признак статуса обработки:
  - ожидает обработки;
  - обрабатывается;
  - распознано;
  - ошибка распознавания;
  - проверено оператором.
- Простая сервисная граница для OCR, чтобы позже можно было заменить провайдера.
- Простая эвристическая экстракция полей из распознанного текста.
- API для просмотра и изменения распознанных данных.
- Тесты на обработку, экстракцию и API.

### Поля постановления

- номер постановления;
- дата постановления;
- УИН;
- сумма штрафа;
- статья / ссылка на КоАП, если видна в документе;
- госномер автомобиля, если виден в документе;
- дата и время нарушения, если видны в документе;
- место нарушения, если видно в документе;
- орган, вынесший постановление, если виден в документе.

### Административная панель

- В деталях дела показать блок распознавания.
- Показать raw OCR text.
- Показать извлечённые поля постановления.
- Добавить форму ручной корректировки полей.
- Показать статус обработки документа.
- Показать ошибку распознавания, если обработка не удалась.
- Дать оператору сохранить исправленные данные.

### Telegram-бот

- После загрузки постановления сообщать, что документ принят и будет обработан.
- Не показывать пользователю автоматический юридический вывод на этой стадии.
- Не обещать генерацию жалобы на этой стадии.

## Что не входит в Стадию 2

- Юридическая проверка постановления.
- Вероятность отмены штрафа.
- Автоматические основания для обжалования.
- Legal Rules Engine.
- LLM.
- Генерация жалобы.
- Генерация DOCX/PDF.
- Оплата.
- Передача дела юристу.
- Интеграция с ЕСИА, ГИС ГМП или партнёрскими API.

## Практический план реализации

1. Добавить модели и миграцию для результата распознавания и карточки постановления.
2. Добавить OCR service с простым интерфейсом и заглушкой/провайдером для первого запуска.
3. Добавить extraction service для базовых полей.
4. Запускать обработку после загрузки документа.
5. Расширить Admin API данными распознавания.
6. Добавить в админку блок просмотра и ручного редактирования карточки постановления.
7. Обновить пользовательские тексты бота под Stage 2.
8. Покрыть backend-тестами основные сценарии.

## Критерии готовности

- После загрузки документа создаётся дело и запускается обработка.
- Raw OCR text сохраняется в базе.
- Извлечённые поля сохраняются в базе.
- В админке видны raw text, поля и статус обработки.
- Оператор может вручную изменить поля.
- Ошибка распознавания отображается в админке.
- Backend-тесты проходят.
- Админка собирается.
- Production deployment на Vercel работает.
